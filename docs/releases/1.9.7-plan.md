## The dashboard migration needs for the release

This app does not run `rails generate action_agent:install`; it copies the
engine's migrations into `db/migrate` with the platform's empty table
prefix, the way 029 became `20261027000001` for 1.9.5. The 1.9.7 repin PR
carries both of these and a `db/schema.rb` dumped from a scratch database
(version `2026_10_30_000002`); the deploy's migrate job applies them on
staging and production.

`db/migrate/20261030000001_add_scoring_leases_to_active_agent_evaluation_scenario_results.rb`
(engine template 030):

```ruby
# frozen_string_literal: true

# The lease a judge job takes on a pending evaluation result while it asks
# the provider to score it, so a duplicate delivery cannot score the result
# again (ActionAgent::ScenarioEvaluationRunner#claim_result!). Copied from
# the engine's install generator (migration 030) with the platform's empty
# table prefix.
class AddScoringLeasesToActiveAgentEvaluationScenarioResults < ActiveRecord::Migration[8.2]
  def change
    prefix = ActionAgent.table_name_prefix

    add_column "#{prefix}evaluation_scenario_results", :scoring_token, :string
    add_column "#{prefix}evaluation_scenario_results", :scoring_expires_at, :datetime
  end
end
```

`db/migrate/20261030000002_add_metadata_to_active_agent_catalog_scenarios.rb`
(engine template 031; jsonb, since the platform is PostgreSQL):

```ruby
# frozen_string_literal: true

# A catalog scenario's extension fields (anything in the document outside
# the format's own keys), kept so export, digests and the dashboard round
# trip them (ActionAgent::CatalogScenario#metadata). Copied from the
# engine's install generator (migration 031) with the platform's empty
# table prefix.
class AddMetadataToActiveAgentCatalogScenarios < ActiveRecord::Migration[8.2]
  def change
    add_column "#{ActionAgent.table_name_prefix}catalog_scenarios", :metadata, :jsonb
  end
end
```

Order matters only for the numbering: 030 before 031, as the engine's dummy
app applies them. Neither touches existing rows; both are additive and
reverse cleanly.

## Release steps

The 1.9.6 recipe ([1.9.6-plan.md](1.9.6-plan.md)): worktree from
`origin/main`, bump the two `version.rb` files and the sidecar's
`package.json` and lock, `## [Unreleased]` → `## [1.9.7] - <date>`, release
PR, merge, tag `v1.9.7` on the merge commit **pushed from a checkout with
push rights** (a cloud session's git proxy refuses tag pushes; 1.9.6 was
published by dispatching the Release workflow instead). Then the repin PR
here with the two migrations above, merge to `main` for staging, migrate
job green, smoke test, production dispatch.

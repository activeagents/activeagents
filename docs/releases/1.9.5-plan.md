## Why passkeys, and why not a TOTP step

The app has no second factor today. `users` holds a `password_digest` and
nothing else for authentication; the Gemfile has `bcrypt` and no OTP or
WebAuthn gem; the only brute-force defence is `rate_limit to: 10, within:
3.minutes` on `SessionsController#create`, `PasswordsController#create`
and `PasswordLinksController#create`.

A passkey is better used as a **sign-in method** than as a second step
after the password:

- The authenticator already verifies the person (Face ID, Touch ID, PIN),
  so one ceremony is two factors.
- The credential is bound to the origin, so it cannot be phished the way
  a password plus a six-digit code can.
- Most sign-ins will come through Google or GitHub, which run their own
  second factor. Password-only accounts are the exposure, and a passkey is
  the cheapest way for those people to stop typing a password at all.

Classic TOTP (code after password, recovery codes) only hardens password
sign-in. Keep it as a later addition under the same Settings section if a
customer needs an enforced second factor; it is not in this release.

## Shape in this codebase

Follows the provider pattern from `docs/github-sign-in.md` and
`docs/google-sign-in.md`: register from Settings while signed in, sign in
from the session page, never auto-link.

| Piece | Plan |
| --- | --- |
| Gem | `webauthn` (cedarcode/webauthn-ruby) on the server. Front end uses the browser `navigator.credentials` API from a Stimulus controller; `@github/webauthn-json` only if the base64url plumbing gets annoying. |
| Schema | `passkeys` table: `user_id`, `external_id` (credential id, unique), `public_key`, `sign_count`, `nickname`, `last_used_at`, timestamps. `users.webauthn_id` (stable random handle, set on first registration). |
| Model | `Passkey belongs_to :user`; `User has_many :passkeys`. `User#signs_in_without?(thing)` grows to count passkeys, so the "set a password before disconnecting your last method" rule in `GithubIdentitiesController#destroy` and the Google twin keeps working, and a passkey can be deleted only when something else remains. |
| Register | `resource :passkeys, path: "settings/passkeys"`: `new` returns creation options (JSON, challenge in the session), `create` verifies the attestation and saves, `destroy` removes one. Behind `require_verified_user!` and the same `rate_limit` as the identity controllers. Settings gets a "Passkeys" section next to GitHub and Google: list with nickname and last used, Add a passkey, Remove. |
| Sign in | `resource :passkey_session, path: "session/passkey"`: `new` returns request options with no `allowCredentials` (discoverable credentials, so no email field), `create` verifies the assertion, bumps `sign_count`, stamps `last_used_at`, starts a session. A third button in `sessions/_providers.html.erb`, "Sign in with a passkey", shown when the browser supports it (`PublicKeyCredential` present), so no server flag. Sign-up page does not get it: a passkey is added after the account exists. |
| Relying party | `WebAuthn.configure` with `rp_name` "Active Agent" and `rp_id` per environment: `localhost` in development, `staging.activeagents.ai` on staging, `activeagents.ai` in production (covers `www.`). `allowed_origins` from the same host. Set through one env var `WEBAUTHN_RP_ID` passed by Terraform from `variables.tf` defaults, same file-first rule as the sign-in flags. |
| Tests | Integration tests with `WebAuthn::FakeClient` for the full register and sign-in ceremonies, the sign-count regression, the last-method rule, and the rate limits. Same files and style as `test/integration/sign_in_with_github_test.rb`. |
| Docs | `docs/passkeys.md` (what it does, the rules, the env var), Settings and sign-in copy in the same voice as the provider docs. |

Not in scope: passkeys at sign-up, TOTP, enforced 2FA per workspace,
device management beyond nickname and last-used, syncing to Resend.

## Operations

Almost none, which is the other reason to start here. No console
registration, no secrets: the public keys live in the database. Each
environment needs its `WEBAUTHN_RP_ID` default and a deploy. The ceremony
needs HTTPS, which staging and production have, or `localhost`, which the
development server is.

## Release gate

1. Register and sign in on `localhost:3000` with a platform authenticator
   (Touch ID in Chrome and Safari) and once with a cross-device passkey
   (phone QR).
2. Same two on `staging.activeagents.ai` after deploy; delete the passkey
   from Settings and confirm the last-method rule refuses when it is the
   only way in.
3. Production deploy, repeat once.
4. Gem side: nothing in this release depends on the gems; tag `v1.9.5`
   only if gem changes have accumulated under `[Unreleased]` by then.

Rough size: one to two days of code and tests, plus the three real-browser
rounds above.

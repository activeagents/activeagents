Design note on Google: the service reads Google's `userinfo` with the
access token instead of verifying the `id_token` against Google's JWKS.
The token arrives over TLS in a client-secret-authenticated exchange and
carries the same claims, so this keeps `GoogleSignIn` the same shape as
`GithubSignIn` (exchange, one read, drop the token) with no JWT
dependency. PKCE is on top of the `state`. Disconnecting a provider is
now refused only while it is the last way in (password or another
provider), for GitHub too.

## Where auth lives

Sign-in is host-app code (`activeagents`), not the gem: sessions,
registrations, `GithubSessionsController`, `user_identities`. The gem's
`config.github_client_id/secret` (ActionAgent) is the repository-access
App for code sessions, a different thing. So "1.9.3" here means the
platform release window that ships alongside the 1.9.3 gem tag, the same
way the production environment (#181) ships with 1.9.2. Nothing in the
gem has to change for either provider.

## GitHub: already built, switched off

[github-sign-in.md](../github-sign-in.md) describes what shipped in #154:
identities keyed on GitHub's numeric id, sign-up from a verified primary
email, no automatic linking by email, Settings connect/disconnect, the
`state` round trip. `test/integration/sign_in_with_github_test.rb` covers
it. Neither environment has it on: `enable_github_sign_in` is false and
the `activeagents-<env>-github-app-client-id/-client-secret` secrets have
no version.

To ship it for 1.9.3 (operations only, no code):

1. Register the production GitHub App (`ActiveAgents`) per
   [gcp-cicd-setup.md](../infrastructure/gcp-cicd-setup.md) §1, callback
   `https://activeagents.ai/auth/github/callback` plus `www` and
   `api`. After the cutover the apex serves production, so the App's
   callbacks name production hosts; staging's App gets
   `staging.activeagents.ai`.
2. Add the client ID and secret versions (§2), then set
   `enable_github_sign_in = true` in
   `terraform/environments/production/variables.tf` (CI applies the
   file's default; a value set anywhere else is lost on the next deploy).
3. Same for staging, so the flow is exercised before production.

Half a day, mostly waiting on GitHub's forms.

## Google: new code, same shape

Mirror the GitHub controller rather than add OmniAuth; the hand-rolled
flow is small, tested, and already owns the identity model.

- **Flow**: OAuth 2.0 authorization code with PKCE, scopes
  `openid email profile`, `state` kept in the session for ten minutes as
  today. The callback exchanges the code, verifies the `id_token`
  signature against Google's JWKS and its `aud`/`iss`/`exp`, and reads
  `sub`, `email`, `email_verified`, `given_name`, `family_name`. No access
  token is stored.
- **Identity**: `user_identities` row with `provider: "google"`,
  `uid: sub`, `email`, `login: nil` (the unique index on provider + uid
  and on user + provider already fits). Same matching rules as GitHub:
  connected identity signs in; unknown `sub` with a verified email that
  has no account creates one (verified, random password, owned
  workspace, on to profile completion); an email that already has an
  account is never linked automatically; `email_verified: false` cannot
  sign up.
- **UI**: a second button on `sessions#new` and `registrations#new`,
  connect/disconnect in Settings with the same "only way to sign in"
  refusal.
- **Config**: `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` from the
  environment or `google_oauth.*` in credentials; Terraform adds
  `google-oauth-client-id` and `google-oauth-client-secret` to the
  secrets map and an `enable_google_sign_in` flag, exactly like the
  GitHub pair, so `terraform/tests/feature_infra.tftest.hcl` gains two
  runs. Per the standing rule, every setting lands in the tf files.
- **Google Cloud**: an OAuth client (web application) in
  `active-agents-platform` with authorized redirect URIs
  `https://activeagents.ai/auth/google/callback` (and `www`, `staging`),
  and the consent screen published to "In production" so any Google
  account can sign in. The basic scopes need no app verification; the
  screen shows the app name and the support email, so the Workspace
  mailbox `hello@activeagents.ai` fits.
- **Tests**: `test/integration/sign_in_with_google_test.rb` modelled on
  the GitHub one, with the token endpoint and JWKS stubbed by WebMock.

About a day of code plus the console setup.

## Why it matters beyond convenience

- OAuth sign-ups arrive verified, so they bypass the email verification
  that the subscription-bombing bot abuses
  ([2026-10-19-signup-bot-email-abuse.md](../issues/2026-10-19-signup-bot-email-abuse.md))
  and do not spend the Resend daily cap.
- Retainer clients on Google Workspace (the pilot client among them) can accept a
  pilot invitation and sign in without a password reset email, which is
  the step that failed in spam on 2026-10-20.

## Not in scope

- SSO/SAML for enterprise (listed under platform-only features) stays a
  separate item.
- Replacing password sign-in: it remains, and the GitHub rules about an
  account's "only way to sign in" extend to Google.

## Codex on staging and production

What exists: both environments run `SANDBOX_BACKEND=incus`
(`terraform/main.tf`). `IncusSandboxService::ClaudeCode#code_runners`
returns `%w[claude_code]`; the app-runtime image installs Claude Code only
(`docker/sandbox/app-runtime/provision.sh`, `install_claude_code`, run by
the image's `sandbox-claude` helper as the `claude` user); and the Incus
backend has no browser MCP wiring for either runner. Nothing in Terraform
or the host initializer mentions Codex.

What "Codex set up" takes, in order:

1. **Image**: install the Codex CLI (pin a version; 0.162.1 is what #612 was
   checked against) for the `claude` user in `provision.sh`, record the
   version as `claude-code-version` is, rebuild and roll the image.
2. **Backend**: `IncusSandboxService::ClaudeCode` advertises
   `%w[claude_code codex]`; the `sandbox-claude` helper gets a Codex mode
   that runs `codex exec --json …` (and `codex exec resume` for later
   turns) with `CODEX_HOME` under `/workspace`, the key as `CODEX_API_KEY`
   in the exec's environment only, and reads Codex's JSONL back as it reads
   Claude Code's stream-json. The engine's `CodexSessionEvents` already
   parses the events.
3. **Auth, first cut**: the workspace's OpenAI API key, which a workspace
   connects itself in Settings → Integrations → Codex. No operator secret
   and no Terraform change: `codex_auth` stays `:api_key`, and
   `:local_login` is refused on Incus by design. Metered, so this is the
   bring-your-own-key tier rather than the subscriber one.
4. **Auth, subscriber login (later)**: a Codex `:sandbox_login` analogue in
   the engine and the helper, on `codex login --device-auth`, gated by a
   `codex_hosted_login_enabled` flag like Claude Code's, after reading
   OpenAI's terms on plan usage from a hosted service.
5. **Browser**: the Incus backend has no per-turn browser token wiring for
   Claude Code either, so "Codex browser" on hosted is the Incus browser
   sidecar item, separate from Codex itself.
6. **Host plumbing**: the initializer reads `CODEX_AUTH` into
   `config.codex_auth` (already drafted, uncommitted, guarded for the 1.9.2
   pin); the 1.9.3 repin PR carries it.

Rough size: items 1 to 3, two to three days with tests on staging; item 4,
two more; item 5 depends on the sidecar-on-Incus design.

Justin, 2026-10-21: "wrap the codex and google auth on a separate new PR that
is focused on the config to setup the app for those services as needed".
This is that PR. It carries the configuration the app needs, and this file
is the checklist of the steps only a person with the Google Cloud and GitHub
consoles can do. Nothing here creates a client, an App or a secret version;
those are the steps below.

## What the PR carries

1. `config/initializers/action_agent.rb`, two settings the hosted app did not
   read before:
   - `config.browser_sidecar_path` from `ACTION_AGENT_BROWSER_SIDECAR_PATH`,
     for a developer running the `:local` sandbox backend against a checkout
     of the browser sidecar. `browser_sidecar_path=` exists in actionagent
     1.9.2, the version `Gemfile.lock` pins, so the line is not guarded.
   - `config.codex_auth` from `CODEX_AUTH` (`api_key`, the default, or
     `local_login` for a developer's own machine on the `:local` backend).
     `codex_auth=` arrives with actionagent 1.9.3 (gem #612, merged to the
     gem's `main` with #606), and 1.9.2 does not have it, so the line is
     behind `if config.respond_to?(:codex_auth=)` until the repin. Terraform
     sets nothing for it: both hosted environments keep `api_key`, and a
     hosted backend refuses `local_login` by design.
2. `terraform/environments/staging/terraform.tfvars.example` and
   `terraform/environments/production/terraform.tfvars.example`: the
   `enable_google_sign_in` example line next to the GitHub one, and a note
   that both secrets of a flag need a version before the flag goes on.
3. Docs: this file, and the first committed copy of
   [1.9.3-plan.md](1.9.3-plan.md) (the `docs/releases/` folder was untracked
   until now; the 1.9.1 and 1.9.2 release notes stay in the main checkout
   for a later docs commit) with a pointer to this PR in its "Release gate"
   section.

What the PR does not change, on purpose:

- The `enable_google_sign_in` and `enable_github_sign_in` defaults in each
  environment's `variables.tf` stay `false`. Cloud Run refuses to start a
  revision that reads a secret with no version, and none of the eight
  sign-in secrets has one yet (checked 2026-10-21, see the table below).
  Flipping a flag in this PR would take down the next deploy of that
  environment. The flips are step 6 below.
- No Terraform variable or secret is added. #186 declares
  `enable_google_sign_in` and the two `google-oauth-client-*` secrets in
  `terraform/main.tf`, `terraform/variables.tf` and both environments; this
  PR does not duplicate them. The example lines name a variable that exists
  once #186 is merged.
- No gem repin. 1.9.3 is not tagged; see "After the tag" below.

## Human steps

Do staging first, production second. Every command below reads a value from
the terminal with `read -rs` (nothing in shell history, nothing on disk) or
from a file you type, and pipes it straight into `gcloud secrets versions
add --data-file=-`. No command prints a secret.

```sh
PROJECT=active-agents-platform
DEPLOY_ENV=staging     # then production
```

### 1. Merge #186 and let the empty Google secrets exist

1. Merge [#186](https://github.com/activeagents/activeagents/pull/186)
   (Sign in with Google) once its review is done. The push to `main` runs
   **Deploy to Staging**, whose `terraform apply` creates
   `activeagents-staging-google-oauth-client-id` and
   `-client-secret` with no version. Nothing reaches the app while the flag
   is off.
2. Production gets its two secrets from the next **Deploy to Production**
   (Actions, `deploy-production.yml`, **Run workflow**; with no `image_tag`
   it redeploys the build the `staging` tag points at).
3. Do not create either secret by hand first: the next apply would fail
   with a 409 on the name.
4. Check, no values printed:
   ```sh
   gcloud secrets list --project=$PROJECT --filter="name:google-oauth OR name:github-app-client" --format="value(name)"
   ```
   Eight names, four per environment, once both environments have applied.

### 2. Google: consent screen (once per project)

Google Cloud console, project `active-agents-platform`:

1. **Google Auth Platform** (left menu, or
   <https://console.cloud.google.com/auth/overview?project=active-agents-platform>;
   the older path is **APIs & Services → OAuth consent screen**).
2. **Branding**: app name `Active Agent`, user support email
   `hello@activeagents.ai`, authorized domain `activeagents.ai`, developer
   contact `hello@activeagents.ai`. The logo is optional and triggers a
   review if set; leave it out for now.
3. **Audience**: user type **External**, then **Publish app** so any Google
   account can sign in. The scopes the app asks for (`openid email profile`)
   are non-sensitive, so publishing needs no verification review.
4. **Data access**: no scopes need adding; the app requests the three
   basic ones at sign-in.

### 3. Google: one OAuth client per environment

Same console, **Google Auth Platform → Clients** (or **APIs & Services →
Credentials → Create credentials → OAuth client ID**):

1. **Create client**, application type **Web application**.
2. Staging: name `ActiveAgents (staging)`, authorized redirect URI
   `https://staging.activeagents.ai/auth/google/callback`.
3. Production: name `ActiveAgents`, authorized redirect URIs
   `https://activeagents.ai/auth/google/callback` and
   `https://www.activeagents.ai/auth/google/callback`. Add
   `https://api.activeagents.ai/auth/google/callback` only if people will
   sign in on that host.
4. Authorized JavaScript origins stay empty; the flow is a server-side
   redirect. Google refuses a redirect URI that is not registered exactly,
   including the scheme and the path.
5. Copy the client ID and the client secret from the client's page. Google
   shows the secret once at creation and again on the client's page; do not
   paste either into a chat, a doc or a commit.

Until the production cutover the apex serves staging, so a production round
trip cannot be tested on `activeagents.ai` yet; staging's client and
`staging.activeagents.ai` are where the first real round trip happens.

### 4. Google: add the two secret versions

Once per environment, after step 1 has created the secrets:

```sh
read -rs GOOGLE_CLIENT_ID && printf %s "$GOOGLE_CLIENT_ID" |
  gcloud secrets versions add "activeagents-$DEPLOY_ENV-google-oauth-client-id" --project=$PROJECT --data-file=-
read -rs GOOGLE_CLIENT_SECRET && printf %s "$GOOGLE_CLIENT_SECRET" |
  gcloud secrets versions add "activeagents-$DEPLOY_ENV-google-oauth-client-secret" --project=$PROJECT --data-file=-
unset GOOGLE_CLIENT_ID GOOGLE_CLIENT_SECRET
```

If you would rather type each value into a file, strip the newline an
editor adds, then delete the file:

```sh
tr -d '\n' < google-client-id.txt |
  gcloud secrets versions add "activeagents-$DEPLOY_ENV-google-oauth-client-id" --project=$PROJECT --data-file=-
rm google-client-id.txt
```

Check (counts only): `gcloud secrets versions list "activeagents-$DEPLOY_ENV-google-oauth-client-id" --project=$PROJECT`
lists one enabled version; same for `-client-secret`.

### 5. GitHub: the App's callback and client secret, then the two versions

Sign in with GitHub is already in `main` (PR #154, `docs/github-sign-in.md`);
only the registration and the secrets are missing. The App is the one
`docs/infrastructure/gcp-cicd-setup.md` ("Register one GitHub App per
environment") describes; one App serves both sign-in and, later, repository
access.

1. If the environment has no App yet, register it at
   <https://github.com/organizations/activeagents/settings/apps/new>:
   name `ActiveAgents (staging)` or `ActiveAgents`, homepage URL the
   environment's public URL, the permissions and the webhook secret as that
   section says.
2. In the App's settings (**Organization settings → Developer settings →
   GitHub Apps → the App → General**), under **Identifying and authorizing
   users**, add a callback URL `https://<host>/auth/github/callback` for every
   host that serves the environment: `https://staging.activeagents.ai/auth/github/callback`
   for staging; `https://activeagents.ai/auth/github/callback` and
   `https://www.activeagents.ai/auth/github/callback` for production.
3. Under **Permissions & events → Account permissions**, set **Email
   addresses** to **Read-only** (`/user/emails` needs it to find the verified
   primary address).
4. Under **General → Client secrets**, **Generate a new client secret**.
   Note the client ID shown on the same page.
5. Add the versions (the two secrets already exist in both environments):
   ```sh
   read -rs CLIENT_ID && printf %s "$CLIENT_ID" |
     gcloud secrets versions add "activeagents-$DEPLOY_ENV-github-app-client-id" --project=$PROJECT --data-file=-
   read -rs CLIENT_SECRET && printf %s "$CLIENT_SECRET" |
     gcloud secrets versions add "activeagents-$DEPLOY_ENV-github-app-client-secret" --project=$PROJECT --data-file=-
   unset CLIENT_ID CLIENT_SECRET
   ```
   The private key and the webhook secret belong to `enable_github_app`
   (repository access), a different flag; sign-in does not need them.

### 6. Turn the flags on, one environment at a time

Only after both secrets of that flag have a version in that environment.
CI applies the defaults in `terraform/environments/<env>/variables.tf`
(plus the committed `*.auto.tfvars` next to it), so the change is a commit,
never a `gcloud run services update`. Each edit is one line, in the
variable's block:

`terraform/environments/staging/variables.tf`:

```diff
 variable "enable_github_sign_in" {
   description = "Pass the GitHub App client ID and secret to the app, which turns on Sign in with GitHub"
   type        = bool
-  default     = false
+  default     = true
 }
```

```diff
 variable "enable_google_sign_in" {
   description = "Pass the Google OAuth client ID and secret to the app, which turns on Sign in with Google"
   type        = bool
-  default     = false
+  default     = true
 }
```

`terraform/environments/production/variables.tf`: the same two hunks (the
blocks are identical apart from the comment naming the production secrets).

The equivalent, per `gcp-cicd-setup.md` step 4, is a committed
`terraform/environments/<env>/github_app.auto.tfvars` holding
`enable_github_sign_in = true` and `enable_google_sign_in = true`; the
`terraform.tfvars.example` files show that form. Pick one place per
environment and keep it there.

Order:

1. Staging: commit the two staging hunks, open a PR, merge. The push to
   `main` deploys staging with `GITHUB_APP_CLIENT_ID/SECRET` and
   `GOOGLE_CLIENT_ID/SECRET` in the service's environment.
2. Check on `https://staging.activeagents.ai/session/new`: **Sign in with
   Google** and **Sign in with GitHub** render; one round trip of each
   (sign up with a fresh account, then connect and disconnect from
   Settings).
3. Production: the same two hunks in its `variables.tf`, merge, then
   **Deploy to Production** (workflow dispatch, or the next release). Its
   round trip can only be checked after the cutover moves the apex to
   production.

If a deploy fails to start a revision with a Secret Manager error, a secret
named by a flag has no version in that environment: set that flag back to
`false`, merge, and add the version before trying again.

## Codex on staging and production: not in this PR

The hosted Codex entry in the Agent menu stays "backend unavailable" after
this PR: both environments run the Incus backend, and
`IncusSandboxService::ClaudeCode#code_runners` still returns
`%w[claude_code]`. The list in [1.9.3-plan.md](1.9.3-plan.md), "Codex on
staging and production", is the work, and none of it is configuration:

1. Image: install the Codex CLI in the app-runtime image
   (`docker/sandbox/app-runtime/provision.sh`) and record the version.
2. Backend: advertise `codex` from `code_runners` and give the
   `sandbox-claude` helper a Codex mode (`codex exec --json`, resume, the
   key as `CODEX_API_KEY` in the exec's environment only).
3. Auth, first cut: the workspace's own OpenAI key from Settings →
   Integrations → Codex; `codex_auth` stays `api_key`, nothing in Terraform.
4. Auth, subscriber login: a `sandbox_login` analogue behind a
   `codex_hosted_login_enabled` flag, after reading OpenAI's terms.
5. Browser: the Incus browser sidecar item, separate from Codex.

This PR's part is item 6 of that list, the `CODEX_AUTH` initializer line.
